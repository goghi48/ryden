# Contributing to Ryden

Thank you for taking the time to improve Ryden. Contributions should make the product easier to use, the code easier to understand, or the service safer to operate.

## Before you start

Search existing issues before opening a new one. For a significant feature, data-model change, or architectural change, open an issue first and describe:

- the user problem;
- the smallest useful solution;
- expected behavior and non-goals;
- API, database, security, and compatibility impact.

Small bug fixes, tests, documentation corrections, and narrowly scoped cleanup can go directly to a pull request.

## Development setup

The simplest local environment uses Docker Compose:

```bash
cp .env.example .env
docker compose up --build
```

The web application runs at [http://localhost:5173](http://localhost:5173), and the API runs at `http://localhost:8080`.

## Make a change

1. Fork the repository and create a focused branch.
2. Keep unrelated formatting or refactoring out of the change.
3. Follow the existing module boundaries and naming style.
4. Validate every state-changing operation and enforce authorization at the resource boundary.
5. Add or update tests for changed behavior and fixed regressions.
6. Update the OpenAPI contract and migrations when the public API or database changes.
7. Run the relevant checks before opening a pull request.

Do not edit files marked `Code generated by sqlc` by hand. Change the SQL query or schema source and regenerate the code with `sqlc generate`.

## Code style

Write code for the next person who will read it:

- prefer small, cohesive functions and explicit names;
- keep Go packages aligned with product domains rather than generic helper packages;
- use `gofmt` and handle errors with enough context to diagnose failures;
- keep I/O bounded and pass `context.Context` through backend operations;
- avoid hidden global state and infrastructure without a measured need;
- keep React components focused and move complete feature areas into their own modules;
- explain why a non-obvious decision exists instead of narrating what the code already says.

## Required checks

Backend:

```bash
go fmt ./...
go vet ./...
go test ./...
```

Frontend:

```bash
cd web
pnpm install --frozen-lockfile
pnpm lint
pnpm typecheck
pnpm test
pnpm build
```

Run integration and load tests when a change affects concurrency, transactions, large lists, uploads, database pressure, or live updates.

## Pull requests

A pull request should:

- solve one coherent problem;
- explain the user-visible result and the reason for the change;
- reference the related issue when one exists;
- include tests and migration or API updates where required;
- call out operational risks, compatibility changes, and follow-up work;
- pass every required CI check.

Use short imperative commit messages. An optional area prefix is welcome, for example:

```text
meeting: preserve attendance after an owner edit
web: simplify the invitation dialog
docs: clarify local setup
```

## Security reports

Do not publish credentials, tokens, invitation links, personal data, or vulnerability details in an issue or pull request. Use GitHub's private vulnerability reporting for security-sensitive findings. Remove sensitive values from logs and screenshots before attaching them anywhere.

Never commit a working `.env`, private key, certificate, backup, or production dataset. If a credential is exposed, rotate it before cleaning Git history.

## Community

Be respectful, stay on topic, and assume good intent. Share only code and content that you have the right to contribute under the project's MIT license.
